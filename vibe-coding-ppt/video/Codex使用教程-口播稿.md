# Codex 使用教程 · 口播稿

### 01. Codex 使用教程

_从安装到团队规范，一条完整上手路线_

> 这组视频用十四个章节的整理稿，讲清 Codex 从安装到团队协作的完整用法。你会先装好桌面 App，再学会写任务、看审查、配置权限。后面还会讲到外部工具、并行子代理和后台自动化。全程用真实命令和版本信息，不靠背参数。


## 第一章 准备

### 02. 认识 Codex，装好第一个入口

_四种入口、安装、认证与排障_

> 先回答一个基础问题，Codex 不是聊天窗口，而是能读写本地项目的开发工具。它有四种入口，桌面 App 是学习主线，命令行、网页与云端、编辑器插件都算补充。这一章把安装、登录和排障一次讲完。装好之后，你就能安全地打开第一个项目。

### 03. Codex 是什么

- 桌面开发主控台，能读写本地项目
- 核心是线程、审查、终端和设置
- 能力受沙盒和审批约束
- App 是主线，其余入口作补充

> Codex 是一个桌面开发主控台，核心能力围绕线程、审查、终端和设置展开。它能读取本地项目、修改文件、在受控环境里运行命令。每一步都受沙盒和审批约束，权限越大，越需要人看结果。学习时先把 App 用顺，再考虑其他入口。

### 04. 四种入口怎么选

| 入口 | 定位 | 适合场景 |
|---|---|---|
| 桌面 App | 开发主控台，学习主线 | 本机项目、线程与审查 |
| 命令行 | 配置、脚本与持续集成辅助 | 排查配置、无头执行 |
| 网页与云端 | 远程仓库执行 | 长任务、PR 评论反复修 |
| 编辑器插件 | 在编辑器内取上下文 | 已有编辑器工作流 |

> Codex 有四种入口，定位各不相同。桌面 App 是主线，适合本机项目的线程管理和结果审查。命令行适合排查配置、写脚本和在持续集成里无头执行。网页与云端适合远程仓库上的长任务。编辑器插件复用已有编辑器上下文，学习阶段先放一放。

### 05. Windows 安装四步

- **从官方页面进商店**：打开官方 Windows 页，点应用链接
- **在商店点获取**：企业禁用商店时让管理员分发，或用 winget
- **开始菜单打开 Codex**：首次启动按提示登录
- **处理防火墙弹窗**：只勾专用网络，公用网络不要选

> Windows 安装走官方页面进微软商店，企业禁用商店时让管理员分发，或者用 winget 安装。装完从开始菜单打开 Codex，首次启动按提示登录。防火墙弹窗只勾专用网络，公用网络不要选。App 装不上时先确认系统版本和安装来源，不要急着重装。

### 06. macOS 安装与首次启动

- **从官方入口下载**：不要用来路不明的第三方安装包
- **处理 Gatekeeper 提示**：按提示到隐私与安全性里放行
- **首次启动登录**：优先用 ChatGPT 或 OpenAI 账号
- **授权项目目录**：只给必要的目录和系统能力

> macOS 从官方入口下载安装包，不要用来路不明的第三方安装包。第一次打开可能被 Gatekeeper 拦住，按系统提示到隐私与安全性里放行。首次启动优先用 ChatGPT 或 OpenAI 账号登录。项目目录权限只给必要范围，不要一上来放开整个磁盘。

### 07. 认证登录的四个要点

- 优先用 ChatGPT / OpenAI 账号
- API Key 不是 App 登录方案
- 登录失败换浏览器或重新授权
- 不要把密钥贴进线程或仓库

> 认证登录优先用 ChatGPT 或 OpenAI 账号，API Key 是命令行的自动化方案，不是 App 的登录方式。登录失败先检查浏览器登录状态、网络和账号权限，换浏览器或重新授权通常能解决。团队功能看不到时，先确认账号加入的工作区。任何情况下都不要把密钥贴进线程。

### 08. 安装成功的五条标准

| 标准 | 你应该看到 |
|---|---|
| App 能打开 | 桌面应用正常启动 |
| 账号能登录 | 显示已登录账号 |
| 项目能添加 | 识别本地 Git 状态 |
| 只读能分析 | 总结项目且不改文件 |
| 改动能审查 | 小改动在审查里看到 diff |

> 安装成功的标准不是终端里有命令，而是 App 真的能用。你要能打开桌面应用、用账号登录、添加本地 Git 项目。创建线程后先让它只读分析，确认它不改文件。再做一个小改动，确认审查面板里能看到 diff。五条都过，才算装好。

### 09. 安装排障总表

| 症状 | 常见原因 | 第一反应 |
|---|---|---|
| App 装不上 | 商店、系统版本或企业策略 | 确认来源和系统更新 |
| 登录失败 | 浏览器登录态、网络、账号权限 | 换浏览器或重新授权 |
| 审查不可用 | 没有 Git 或项目不是仓库 | 装 Git 并确认状态命令 |
| 命令跑不动 | PowerShell 策略或工具缺失 | 先在终端跑版本命令 |

> 排障先定位症状，不要反复卸载重装。App 装不上，多半是商店、系统版本或企业策略限制，先确认来源和系统更新。登录失败先查浏览器登录态和账号权限。审查面板不可用，通常是没装 Git 或项目不在仓库里。命令跑不动时先在终端跑版本命令，确认工具链。


## 第二章 App 工作台

### 10. 把 App 当开发主控台

_线程、隔离、审查、设置与第一个任务_

> 第二章讲 App 的桌面工作流。App 不是聊天窗口，它把线程、隔离工作区、审查面板和设置放在同一个界面。这一章你要学会看懂这些区域，然后完成第一次只读分析和第一个小改动。任务怎么写、改动怎么审，都会给出模板。

### 11. App 界面四要素

| 能力 | 作用 |
|---|---|
| Thread | 一条任务线，带上下文和状态 |
| Local workspace | 当前本机项目目录 |
| Worktree | 隔离的 Git 工作目录 |
| Review | 查看 diff、反馈和暂存 |
| Settings | 模型、审批、沙盒和插件入口 |

> App 的界面要认清几个区域。Thread 是一条任务线，带上下文、历史和状态。Local workspace 是当前打开的本机目录。Worktree 给任务一个隔离的 Git 工作目录，降低互相覆盖的风险。Review 面板看 diff 和行内反馈，Settings 管模型、审批、沙盒和插件。

### 12. 一条线程的生命周期

- **开场只读**：先读项目，确认技术栈、命令和风险
- **明确任务**：写清目标、范围、约束和验证方式
- **允许执行**：小任务直接改，大任务先规划或用隔离区
- **检查与收口**：看审查，定点反馈，由人决定是否提交

> 一条线程有完整的生命周期。开场先只读，确认技术栈、启动命令和风险点。然后明确任务，写清目标、范围、不能做什么和怎么验证。小任务可以直接改，大任务先规划或者放到隔离工作区。最后看审查面板，定点反馈，是否提交由人决定。

### 13. 第一次打开项目

- **选一个普通 Git 仓库**：不要一上来打开生产仓库，最好有 README
- **添加本地项目目录**：确认 App 能识别 Git 状态
- **创建 Local thread**：先发只读任务，不改文件
- **再做一个小改动**：只改一个错别字，看 diff 不自动提交

> 第一次打开项目，选一个普通的 Git 仓库，不要一上来就打开生产仓库。添加本地目录后，确认 App 能识别 Git 状态。创建 Local thread，先发一个只读任务。确认只读正常，再做一个最小的改动，比如改文档里的一个错别字，看 diff 但不要自动提交。

### 14. 第一个只读任务

```
阅读这个项目，告诉我：
技术栈、启动命令、测试命令，
以及你建议写进 AGENTS.md 的内容。
不要修改文件。
```

> 第一个只读任务可以这样写：阅读这个项目，告诉我技术栈、启动命令和测试命令，以及你建议写进 AGENTS 点 M D 的内容，不要修改文件。如果它开始尝试改文件，立刻停下并重新强调只读。这一步的目标是确认它能读懂项目，而不是产出改动。

### 15. 第一个安全小改动

- **限定低风险文件**：只改文档里的一个错别字
- **要求展示 diff**：明确说不要自动提交
- **确认改动范围**：改动只在预期文件里
- **演练撤销**：知道怎么撤销或继续修改

> 只读正常后做第一个安全小改动。限定在低风险文件，比如文档里的一个错别字。明确要求改完展示 diff，不要自动提交。然后确认改动只在预期文件里，审查面板能看到。最后演练一次撤销，知道怎么回退或继续修改。

### 16. 好任务写清五件事

| 要素 | 写法 |
|---|---|
| 目标 | 这次要解决什么问题 |
| 范围 | 只改哪些文件或目录 |
| 约束 | 不做什么，例如不新增依赖 |
| 验证 | 跑哪条命令确认改对了 |
| 交付 | diff 摘要、测试结果或 PR 描述 |

> 好任务要写清五件事。目标说明这次解决什么问题，范围限定只改哪些文件和目录。约束写清不能做什么，比如不引入新依赖。验证给出具体命令，确认改动正确。交付说明你要什么，是 diff 摘要、测试结果还是 PR 描述。只写帮我修一下，Codex 不知道边界。

### 17. 任务模板：小范围修复

```
目标：修复 docs/install.md 命令不一致。
范围：只改 docs/install.md。
约束：不改 README，不新增图片，不提交。
验证：检查文内命令前后一致。
交付：给出 diff 摘要和检查过的命令列表。
```

> 这是小范围修复任务的模板。目标写清修什么，范围限定只改一个文件。约束写明不改 README、不加图片、不提交。验证说明怎么确认前后一致。交付要求 diff 摘要和检查过的命令列表。把这几行换成你的任务，Codex 的改动范围会明显收窄。

### 18. Review 面板逐项检查

- **文件列表**：是否只改任务范围内的文件
- **单文件 diff**：是否有无关格式化、删除或重命名
- **命令记录**：验证命令是否真的跑过
- **安全项**：是否碰了环境变量文件、token 或权限

> 审查面板要逐项检查，不要只看结论。先看文件列表，确认只改了任务范围内的文件。再看单个文件的 diff，检查有没有无关的格式化、删除或重命名。命令记录确认验证命令真的跑过，没跑要说明原因。最后看安全项，一旦碰到环境变量文件、token 或权限配置就立即停下。

### 19. 提交与合并关口

- 提交信息可以让 Codex 草拟
- 暂存、提交、推送由人确认
- 推送前确认分支不是 main
- PR 描述写 Summary 和 Verification

> 提交和合并的关口必须由人把守。提交信息可以让 Codex 草拟，但暂存、提交和推送要你确认。推送前确认分支不是 main，最好用功能分支或隔离工作区。PR 描述写清 Summary、Verification 和 Risk，没跑过的检查不要写通过。能看懂 diff，才算真正掌握 App。


## 第三章 命令入口

### 20. 用命令切换工作模式

_斜杠命令的范围、状态与审查_

> 第三章讲命令入口。斜杠命令的价值不是背命令表，而是快速切换工作模式。看状态用斜杠 status，规划用斜杠 plan，长目标用斜杠 goal，审查用斜杠 review，查外部工具用斜杠 mcp。模式不对，命令反而会制造混乱。

### 21. 斜杠命令的三层

- 入口层：status、mcp、feedback
- 状态层：plan、goal 改变推进方式
- 审查层：review 围绕当前 diff 检查
- 命令只是更快进入某种工作模式

> 斜杠命令可以分三层理解。入口层看状态和已连接的工具，比如斜杠 status 和斜杠 mcp。状态层改变任务推进方式，斜杠 plan 让 Codex 先别动手，斜杠 goal 让目标跨多个回合存在。审查层是斜杠 review，围绕当前 diff 做检查。它只是更快进入某种模式，不是能力的开关。

### 22. 五个常用命令

| 命令 | 用途 |
|---|---|
| /status | 查看模型、工作区、审批和上下文 |
| /plan | 大任务先规划，不急着改文件 |
| /goal | 让清楚的目标跨多个回合推进 |
| /review | 审查当前改动，合并前使用 |
| /mcp | 查看已连接的工具服务 |

> 有五个命令值得先掌握。斜杠 status 查看模型、工作区、审批和上下文状态。斜杠 plan 用于大任务，先规划不急着改文件。斜杠 goal 让有边界的目标跨多个回合持续推进。斜杠 review 审查当前改动，合并前使用。斜杠 mcp 查看外部工具服务是否连接正常。

### 23. /plan：好计划包含什么

- 要读哪些文件、要改哪些文件
- 可能方案和取舍
- 验证命令，以及明确不做什么
- 什么时候退出计划进入执行

> 斜杠 plan 要产出一份好计划。它要列出读哪些文件、改哪些文件，给出可能方案和取舍。还要写清验证命令，以及这次明确不做什么。最后说明什么时候退出计划进入执行。差的计划只写做一个完整优化，缺对象和边界，不能照着做。

### 24. /goal：长目标也要有边界

| 适合 | 不适合 |
|---|---|
| 长迁移、长重构 | 目标没有范围，例如优化项目 |
| 部署重试直到成功 | 没有结束条件 |
| 原型打磨到测试通过 | 没有权限边界 |
| 有明确终点的长任务 | 周期检查应交给自动化 |

> 斜杠 goal 适合有明确终点的长任务，比如长迁移、长重构，或者部署重试直到成功。它不适合目标没有范围、没有结束条件、没有权限边界的任务。周期性或后台检查应该交给自动化，不要用 goal 硬扛。用 goal 时一定写清停止条件。

### 25. /review 的五个检查维度

| 维度 | 检查什么 |
|---|---|
| 范围 | 是否只改了任务指定文件 |
| 正确性 | 边界条件、空值、异步竞态 |
| 安全 | 是否触碰密钥、权限、网络 |
| 测试 | 是否覆盖新增行为 |
| 可维护 | 是否引入重复逻辑或隐式依赖 |

> 斜杠 review 围绕五个维度检查。范围看是否只改了任务指定的文件，正确性看边界条件、空值和异步竞态。安全看是否触碰密钥、权限和网络，测试看是否覆盖新增行为。可维护看有没有引入重复逻辑或隐式依赖。真正的重点是范围、安全和测试这三项。


## 第四章 项目指令与权限

### 26. 让 Codex 知道边界

_项目说明文件、配置四层、沙盒与审批_

> 第四章讲项目指令和权限。配置从软到硬分四层，新手先掌握项目说明和 App 设置这两层。项目说明文件 AGENTS 点 M D 写项目事实和安全边界。权限由沙盒和审批共同控制。改完配置要用斜杠 status 或设置页核对是否真的生效。

### 27. AGENTS.md 推荐结构

| 模块 | 要回答的问题 |
|---|---|
| 项目概览 | 这个项目是什么，主要目录在哪 |
| 常用命令 | 安装、测试、lint、build 怎么跑 |
| 修改边界 | 哪些可以改，哪些要谨慎 |
| 代码风格 | 当前项目已有的写法是什么 |
| 验证方式 | 改完怎么证明，失败要解释 |

> AGENTS 点 M D 应该像项目交接文档，不是口号墙。它先写项目概览，说明项目是什么、目录在哪。再写常用命令，安装、测试、lint、build 怎么跑。然后写修改边界和代码风格。最后写验证方式，改完怎么证明，失败要解释。写作顺序是先事实、再规则、最后禁止事项。

### 28. AGENTS.md 不该写什么

- API Key、token、cookie
- 只针对本次任务的临时要求
- 个人机器路径和不稳定的版本号
- 写高质量代码这类无法验证的口号

> AGENTS 点 M D 有几类内容不能写。API Key、token、cookie 这类凭据一律不写。只针对本次任务的临时要求也不要放进去。个人机器路径和不稳定的版本号会让文件很快失效。写高质量代码这种无法验证的口号同样没有信息量。

### 29. 多层 AGENTS.md

```
repo/
  AGENTS.md            # 全局规则
  apps/web/AGENTS.md   # 子目录局部规则
  packages/api/AGENTS.md
```

> Monorepo 可以在根目录和子目录放多份 AGENTS 点 M D。根目录写全局规则，子目录写局部规则。越靠近当前文件的指令越具体。如果根目录和子目录规则冲突，不要让 Codex 猜，先让它报告冲突，再由人决定哪条适用。子目录文件要写明自己的适用范围。

### 30. 配置系统的四层

- 项目说明层：AGENTS.md 写事实和边界
- 用户偏好层：App Settings 设模型、审批、沙盒
- 命令策略层：Rules 拦危险命令
- 事件脚本层：Hooks 做审计和检查

> 配置系统从软到硬分四层。项目说明层是 AGENTS 点 M D，写项目事实、命令和安全边界。用户偏好层是 App 设置和 config 点 toml，设模型、审批、沙盒和外部工具。命令策略层是 Rules，硬性拦截危险命令。事件脚本层是 Hooks，在特定时机运行脚本做审计。新手先掌握前两层。

### 31. 三种沙盒模式

| 模式 | 含义 |
|---|---|
| read-only | 只读，适合审计和探索 |
| workspace-write | 可写工作区，适合日常开发 |
| danger-full-access | 无沙盒限制，只在外部可信环境用 |

> 沙盒有三档。read only 只读，适合审计和探索。workspace write 允许在工作区内写入，适合日常开发。danger full access 移除本地限制，只能在外部已经隔离的可信环境里用。权限越大，越需要审查、Git 和备份。如果只是为了少点弹窗就开最高权限，出事后很难排查。

### 32. 审批与沙盒基线

| 场景 | 审批 | 沙盒 |
|---|---|---|
| 只读审计 | 不允许写入 | read-only |
| 日常开发 | 危险命令审批 | workspace-write |
| 陌生仓库 | 保守审批 | read-only 起步 |
| 持续集成 | 外部隔离加最小权限 | 看运行环境 |
| 生产数据 | 默认拒绝 | 人工授权 |

> 审批模式要判断哪些动作需要人批准。读文件和跑只读命令默认允许。安装依赖、改锁文件、跑迁移、改权限和支付代码、访问项目外目录都要弹审批。命令行常用的审批策略是 on request 和 never，团队不要默认用 never，更不要用跳过审批的绕过参数。

### 33. Rules 适合与不适合

| 适合 | 不适合 |
|---|---|
| 拦危险删除，例如递归删除 | 写复杂业务流程 |
| 拦未经确认的发布和推送 | 替代测试或审查 |
| 允许只读命令 | 判断产品取舍 |
| 对强制推送要求确认或拒绝 | 管理外部账号授权 |

> Rules 比 AGENTS 点 M D 更硬，它参与命令执行策略。适合拦递归删除、未经确认的发布和直接推 main，也适合放行只读命令。不适合写复杂业务流程、替代测试和审查，也不适合管理外部账号。上线前用官方的规则检查命令验证是否按预期命中。能用 Rules 解决的边界，先不要写 Hook。


## 第五章 能力扩展

### 34. 从外部工具到并行与后台

_M C P、Skills、插件、子代理、自动化、云端与命令行_

> 第五章把能力扩展开。M C P 让 Codex 连接外部工具和数据。Skills 把重复提示变成可复用工作流。插件和连接器接入外部账号，子代理把任务并行拆分。自动化让 Codex 按时间在后台醒来。云端负责远程仓库执行，命令行负责排障和持续集成。

### 35. App 中的 MCP 工作流

- **启用或配置**：在 App 设置或集成入口启用 M C P
- **查看可见工具**：回到线程，用斜杠 mcp 看服务
- **用自然语言调用**：要求 Codex 使用工具，观察权限提示
- **审查结果**：核对来源、时间、权限和副作用

> M C P 是工具连接层，让 Codex 连接浏览器、数据库、文档和内部接口。在 App 里先启用或配置，回到线程用斜杠 mcp 查看服务和工具。然后用自然语言要求它调用，注意权限提示。最后审查结果，核对来源、时间、权限和副作用。配置前先确认数据范围、账号密钥和默认读写能力。

### 36. MCP 安全四问

- 它能读什么、能写什么数据
- 它是否联网、是否需要账号授权
- 它是否会把数据发给第三方
- 生产库和客户数据默认不给

> 配置 M C P 前先问四个安全问题。它能读什么数据、能写什么数据。它是否会联网、是否需要账号授权。它是否会把数据发给第三方。生产库、客户数据和邮箱都按最小权限配置。工具风险分四级，只读搜索风险低，写外部系统风险高，访问生产数据默认不要给新手练习。

### 37. Skill 的定位与复用信号

- 一组可复用指令、资源和脚本
- 适合审查、核对、发布检查和团队流程
- 同一提示复制三次以上就值得做
- 一次性任务和定时任务不要做成 Skill

> Skill 是一组可复用指令、资源和可选脚本，本质是可复用的判断流程，不是提示词收藏。适合代码审查、文档核对、发布检查和团队流程。同一个提示复制三次以上，多人需要同一做法，输出格式总要固定，就值得做成 Skill。只做一次的临时任务和需要定时运行的任务都不适合。

### 38. Plugins 与 Connectors 四个概念

| 概念 | 本质 |
|---|---|
| Connector | 外部账号连接 |
| Plugin | 能力包，可能含 Skill 和 M C P |
| Skill | 可复用工作流 |
| M C P | 工具协议 |

> 安装、授权、调用是三件不同的事。连接器是外部账号连接，比如 GitHub、Gmail、Drive 和 Slack。插件是能力包，可能同时带 Skill、M C P 和配置。Skill 是可复用工作流，M C P 是工具协议。安装让能力可见，授权让数据可用，审批是最后的安全门，卸载时要记得撤销外部授权。

### 39. Subagents 启动前四件事

- **总目标**：这次到底要迁移、重构或修好什么
- **子任务边界**：每个代理只读或只改哪些文件
- **是否允许写**：先只读分析，还是限定文件写入
- **汇总与停止条件**：输出证据和风险，遇问题先汇报

> Subagents 把任务拆成多个相对独立的子任务，价值是并行和分工。主线程负责目标、拆分、合并和最终决策。启动前写清四件事：总目标、子任务边界、是否允许写、汇总与停止条件。没有文件所有权，并行只会把混乱一起放大。先学会少用，再学会并行。

### 40. 并行不是越多越好

| 子任务关系 | 是否适合并行 |
|---|---|
| 读不同模块、互不依赖 | 适合 |
| 一个查文档，一个查代码 | 适合 |
| 多个代理都改同一核心文件 | 不适合 |
| 后一步必须等前一步结论 | 不适合 |

> 并行不是越多越好。读不同模块、互不依赖适合并行。一个查文档、一个查代码也适合。多个代理都要改同一个核心文件不适合，后一步必须等前一步结论也不适合。并行写入的命脉是文件所有权，共享文件要由主线程统一修改。合并时先看证据，再看结论是否冲突。

### 41. Automations 三类任务与权限

| 类型 | 示例 | 权限建议 |
|---|---|---|
| 摘要 | 每周总结待办问题 | 只读 |
| 检查 | 每天运行测试或 lint | 只读或最小写入 |
| 修复 | 自动修小问题并提交 PR | 明确范围和审查 |

> 自动化让 Codex 在后台或按计划执行重复任务。项目级自动化依赖本机环境，机器要开机、App 要在运行、目录要存在。三类任务里，摘要和检查优先只读，修复必须明确范围和审查。后台提示词要写清频率、范围、动作、权限和停止条件，否则会反复失败或者产生你没看见的副作用。

### 42. Web/Cloud 还是本机 App

| 情况 | 优先 |
|---|---|
| PR 评论反复修 | Cloud |
| 长时间测试或构建 | Cloud |
| 需要本机数据库或桌面界面 | App |
| 需要访问未推送的本机文件 | App |

> 网页和云端是远程执行路径，不是更强的本地 App。它围绕已连接的远程仓库、分支和 PR 工作，看不到你本机未保存、未提交、未推送的文件。PR 评论反复修、长时间测试或构建、从手机派任务，优先用云端。需要本机数据库、桌面界面或未推送文件时留在 App。云端完成不等于可以合并。

### 43. CLI 常用命令

| 命令 | 用途 |
|---|---|
| codex --help | 查看本机支持项 |
| codex | 进入终端交互界面 |
| codex exec | 无头执行一次任务 |
| codex review | 在终端审查当前改动 |
| codex doctor | 诊断环境和配置 |

> 命令行是 App 的补充，不是普通用户的第一入口。它适合排查配置、管理 M C P、在持续集成里无头执行。常用命令有查看帮助、进入交互界面、无头执行、终端审查和诊断环境。命令行的帮助输出比教程里的静态列表可靠，先跑版本和诊断命令，再看帮助。

### 44. PR 前核对清单

| 项 | 你应该看到 |
|---|---|
| 分支 | 不是直接在 main 上提交 |
| Diff | 没有范围外改动 |
| 测试 | 运行相关测试或说明原因 |
| 描述 | Summary、Verification、Risk |
| Secret | 没有密钥、token 或账号信息 |

> GitHub 和 PR 环节的核心是合并前必须有人看。审查面板读的是 Git 仓库状态，小修看最后一轮，大合并看整个分支。PR 描述不是营销文案，Summary 写具体改了什么，Verification 写真实运行的命令和结果，Risk 写影响范围和未覆盖点。没跑过的检查不要写通过。


## 第六章 安全与团队

### 45. 把权限、密钥和责任说清楚

_安全红线、密钥管理、风险分级与团队规范_

> 第六章讲安全与团队。安全不是单个开关，而是一套分类、限制、记录、复核和响应的流程。最小权限放在前面，风险动作放到不同控制点上。这一章会讲安全红线、密钥管理、风险分级和团队规范。目标是把大家都知道，变成有人负责。

### 46. 安全红线

- 不读取环境变量文件，不打印或提交密钥
- 不自动推送 main，不自动删除
- 不自动合并 PR，不默认跳过审批
- 失败超过两次就停下汇报

> 安全红线要写清楚。不读取环境变量文件，不打印或提交密钥。不自动推送 main，不自动删除，不自动合并 PR。团队不要默认开启跳过审批和沙盒的绕过参数。后台任务失败超过两次就停下汇报，不要无限重试，也不要第一次失败就放大权限。

### 47. 密钥放哪里

| 场景 | 推荐 | 不推荐 |
|---|---|---|
| 本地个人 token | 系统环境变量或密码管理器 | 写进配置并提交 |
| 团队共享服务 | 组织密钥管理、最小范围 | 共享个人账号 token |
| 云端远程 | 环境变量或官方密钥入口 | 在日志里输出密钥 |
| 临时调试 | 临时只读 token，用完撤销 | 使用生产写 token |

> 密钥管理按场景区分。本地个人 token 放系统环境变量或密码管理器，不要写进配置文件再提交。团队共享服务用组织密钥管理和最小范围，不要共享个人账号 token。云端用环境变量或官方密钥入口，不要在日志里输出。临时调试用临时只读 token，用完立即撤销。

### 48. 风险分级与处理

| 级别 | 判断 | 处理 |
|---|---|---|
| 低 | 只读公开文档、改非关键文档 | 普通审查 |
| 中 | 改业务代码、跑测试 | 可写工作区加审查和测试 |
| 高 | 改权限、依赖、部署、数据库 | 计划、审批、隔离工作区 |
| 极高 | 生产写入、密钥、自动合并 | 专门审批和事故预案 |

> 风险分级帮助你先判断再决定动作。低风险是只读公开文档和改非关键文档，走普通审查。中风险是改业务代码、跑测试、读内部文档，用可写工作区加审查和测试。高风险是改权限、依赖、部署和数据库，要先计划、审批、用隔离工作区。极高风险包括生产写入和密钥，默认不让 Codex 自动做。

### 49. 团队规范

- 写清谁能改配置、谁能装插件
- 登记插件、连接器、M C P 和自动化
- 每条外部能力有负责人和撤销方式
- 配置变更像改代码一样走审查

> 团队规范要把口头偏好变成可执行规则。写清谁能改配置、谁能安装插件、哪些 M C P 允许使用、哪些目录禁止写入、自动化任务谁负责。插件、连接器、M C P 和自动化都要有登记表，写明来源、权限、负责人和撤销方式。配置变更也要像改代码一样走审查流程。


## 第七章 上手路线

### 50. 20 分钟上手，30 天落地

_快速路径、月度计划、常见问题_

> 最后一章给出上手路线。如果你刚装好 App，先用二十分钟走一遍只读、描述任务、看懂 diff 和基本操作。然后按三十天计划逐步建立控制感、项目规则、外部能力和后台任务。最后回答几个最常见的问题。

### 51. 20 分钟上手

- **读核心模型**：认线程、工作区和审查面板
- **看三种工作方式**：本机、隔离工作区、云端怎么选
- **记任务模板**：目标、范围、约束、验证、交付
- **走一遍审查**：看文件列表、diff 和命令记录

> 二十分钟快速上手只看四部分。先花五分钟认识核心模型，知道线程、工作区和审查面板在哪里。再用五分钟搞清三种工作方式怎么选。然后花五分钟记住任务模板的五个要素。最后五分钟走一遍审查，能描述任务、看懂 diff、做基本操作，就算过关。

### 52. 30 天落地计划

- **第 1 周：建立控制感**：只读总结、改 README、看审查，不自动提交
- **第 2 周：建立项目规则**：写根 AGENTS.md，明确命令和安全边界
- **第 3 周：接入外部能力**：只读接入 GitHub、M C P、插件并登记
- **第 4 周：并行后台云端**：隔离工作区、只读子代理、自动化和云端

> 三十天计划分成四步。第一周建立控制感，只读总结、改 README、看审查，不自动提交。第二周建立项目规则，写根 AGENTS 点 M D，明确命令来源和安全边界。第三周只读接入 GitHub、M C P 和插件，做好登记。第四周再上隔离工作区、只读子代理、后台自动化和云端。每一周都先跑通只读、审查和回滚的闭环。

### 53. 常见问题 FAQ

- App 只能聊天吗：不是，它是开发主控台
- 所有功能都要学吗：先掌握核心四样
- 执行中能打断吗：可以，直接发新指令
- 什么时候用云端：任务可复现、适合远端

> 最后回答几个常见问题。App 不是只能聊天，它是本地开发主控台。不需要一次学完所有功能，先掌握线程、审查、命令和 AGENTS 点 M D。Codex 执行中可以打断，直接发新指令收窄方向，越早打断越容易控制改动。什么时候用云端？任务可复现、依赖明确、适合远端执行的时候。

### 54. 先建立控制感，再逐步放开能力

_从只读到小改，再到审查与协作_

> 到这里，Codex 的主线用法就讲完了。先用只读建立信任，再做小范围改动，最后用审查收口。权限、沙盒、外部工具和自动化都按最小必要逐步放开。记住一句话，改动是否进入代码库，始终由人决定。
