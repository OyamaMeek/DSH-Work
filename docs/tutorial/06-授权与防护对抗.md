# 06 授权与防护对抗

## 1. 常见授权模型

| 模型 | 特征 | 强度 |
| --- | --- | --- |
| 本地静态校验 | 写死一个字符串或哈希，`if (key == "xxx")` | 极弱，改一个跳转就破 |
| 本地签名校验 | RSA/Ed25519 验签许可证文件 | 中，去掉校验点即可 |
| 设备码 + 卡密 | 设备码提交服务器，返回绑定该设备的令牌 | 中强，需要联网 |
| 远程策略 + 能力数组 | 服务端下发 `{authorized, capabilities[]}`，客户端按能力逐个判断 | 强，改一个点能全开但要找到那个点 |
| 远程策略 + 定期回连 | 上面的基础上定期刷新、支持远程封禁 | 强，需处理离线缓存 |

本项目的样本属于最后一种，拆解见 `reconstructed/walkthrough/01-authorization.md`。

## 2. 自己写一套：设备码 + 签名 + 能力

**客户端**（tweak 侧）：

```objc
+ (NSString *)deviceCode {
    // 用 IDFV + 机型 + 一个随机盐，取 SHA256 前 16 位，够稳定也够短
    NSString *idfv = [[[UIDevice currentDevice] identifierForVendor] UUIDString];
    NSString *raw = [NSString stringWithFormat:@"%@|%@|%@", idfv,
                     [self machineName], @"sjj-salt-2026"];
    NSData *digest = [raw dataUsingEncoding:NSUTF8StringEncoding].SHA256;
    return [digest base64EncodedStringWithOptions:0].substringToIndex:16;
}
```

**服务端**只做一件事：验卡密、把能力数组和设备码绑一起，用私钥签名后返回。

**客户端校验**：

```objc
BOOL SJJVerifyPolicy(NSData *payload, NSData *signature) {
    SecKeyRef key = SJJLoadPublicKey();   // DER 里的 RSA 公钥
    if (!SecKeyIsAlgorithmSupported(key, kSecKeyOperationTypeVerify,
            kSecKeyAlgorithmRSASignatureMessagePKCS1v15SHA256)) return NO;
    return SecKeyVerifySignature(key, kSecKeyAlgorithmRSASignatureMessagePKCS1v15SHA256,
                                 (__bridge CFDataRef)payload,
                                 (__bridge CFDataRef)signature, NULL);
}
```

**能力判定**统一入口（本项目就是这么做的）：

```objc
BOOL SJJCapabilityAllowed(NSDictionary *claims, NSString *cap) {
    if (cap.length == 0) return NO;
    if (![claims[@"authorized"] boolValue]) return NO;
    if ([claims[@"blocked"] boolValue]) return NO;
    id list = claims[@"capabilities"];
    if (![list isKindOfClass:NSArray.class]) list = @[];
    return [list containsObject:cap];
}
```

好处：新增功能只加能力键，不用改判定逻辑；服务端可以精确封禁某台设备的某个能力。

## 3. 对抗：分析别人的插件

识别保护手段的信号：

| 信号 | 含义 |
| --- | --- |
| 导入 `SecKeyVerifySignature`、`SecKeyCreateWithData` | RSA/EC 验签 |
| 导入 `CCHmac`、`CCCrypt` | 对称加密或 HMAC 完整性校验 |
| 导入 `ptrace`、`sysctl` | 反调试 |
| 字符串里有 `__RESTRICT`、`DYLD_INSERT_LIBRARIES` | 反注入 |
| 自定义节（`__sjjprot` 之类） | 密钥/签名数据 |
| `eor x16, x30, x30, lsl #1; tbz; brk` | 不透明谓词陷阱 |

定位方法就是第 2 篇的流程：字符串 → 交叉引用 → 函数语义 → 调用点。

## 4. 对抗：反调试与完整性

宿主或插件可能加这些防护，先认出来再决定要不要处理：

```objc
// 反调试：拒绝被 ptrace attach
ptrace(PT_DENY_ATTACH, 0, 0, 0);

// 检测调试器
int mib[4] = {CTL_KERN, KERN_PROC, KERN_PROC_PID, getpid()};
struct kinfo_proc info; size_t size = sizeof(info);
sysctl(mib, 4, &info, &size, NULL, 0);
if (info.kp_proc.p_flag & P_TRACED) { exit(0); }
```

完整性校验通常是「读自己的 `__TEXT` 算哈希」或「验证签名数据段」。
如果校验的是**代码段**，任何字节补丁都会触发；这时只能走运行时 hook（Frida 或注入 dylib），
不改文件。如果校验的是**数据段**（本项目的 `SJJPKG1`），改代码是安全的。

## 5. 边界

分析别人的插件、给自己的插件加授权，都是本地研究。给别人做破解再分发是另一回事，
后果由操作者承担；技术上这里只讲方法。
